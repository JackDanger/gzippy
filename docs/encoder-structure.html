Structural difference from Sheet 2, in one line: T=1 parses the input in place and drains bytes to the fd as it goes; T>1 copies every input byte into a per-chunk staging buffer and holds the entire compressed output in slot memory until the writer drains it.

SHEET 8

Structural findings

What the drawing makes obvious that a file-by-file read does not.

  1. Per-block allocation is entirely in the Huffman builderalloc

    Of the whole encoder, exactly one function allocates per DEFLATE block: make_huffman_code (huffman/fast.rs:409-410), two Vecs per call, three calls per block — litlen at parse/mod.rs:848, offset at :853, precode inside build_dynamic_header at header.rs:193. Six allocations per block, sized 288/1,152 (litlen), 32/128 (offset) and 19/76 (precode) bytes. Everything else in the parse core is either pooled or hoisted to the run() call. The fix in flight on perf/no-per-block-alloc — caller-owned Huffman codes — closes the last cadence class.

  2. The pooling is asymmetric: the matchfinder is recycled, the 2.8 MB sequence store is notalloc

    HcMatchfinder (262 KB) has a thread_local pool (hc.rs:100, :205) explicitly because "chunk count can exceed thread count". The L1 head tables have the same treatment (fast.rs:2765-2805). But Sink::new() — 2,796,896 bytes, ten times larger — is called fresh at greedy.rs:82, lazy.rs:94 and fast.rs:2931 on every parser invocation, i.e. per streaming pass at T1 and per chunk at T>1. near_optimal.rs:92-97 records having already learned this lesson one level down (it pooled Sink across blocks after DHAT named it) without carrying it up to the call that creates the Sink in the first place. Same for BtMatchfinder::new() (near_optimal.rs:506, 524 KB, unpooled) and the 6.0 MB + 2.4 MB Optimizer.

  3. The T>1 path copies the entire input for no structural reasoncopy

    The input arrives as one contiguous mmap (io.rs:272). The scheduler hands each worker a slice of it plus the 32 KiB immediately before it (scheduler.rs:268-277) — two adjacent regions of the same mapping. encode_deflate_segment_to_sink then allocates a new buffer and copies both into it (deflate/mod.rs:166-169), purely so the buffer ends in BUF_PAD zeros. Every chunk but the last already has readable bytes past its end. The T1 path solved exactly this with encode_deflate_slack_padded_to_sink (mod.rs:265) and the T>1 path never got the equivalent — so T>1 pays 1× input in copies and ~1× input in allocations that T1 does not.

  4. L1 and L10-12 re-read the whole input with no size hintcopy

    level_streams (deflate/mod.rs:571) admits only L0 and the Greedy/Lazy/Lazy2 levels, so L1, L10, L11 and L12 fall to mod.rs:636: Vec::new() then read_to_end. The exact length is known two frames up — compress_with_pipeline_sized takes a size_hint (compress/mod.rs:96) that io.rs:299 fills from metadata().len() — and it is dropped at compress/mod.rs:156 before encode_gzip_reader_to_writer is called. The fallback therefore pays doubling reallocs plus a resize, and holds ~1.5× the input resident. Threading the hint through is a signature change, not an algorithm change.

  5. The RFC 1951 fixed Huffman code is rebuilt from frequency tables on every parser entryalloc

    StaticCodes::build (parse/mod.rs:202-217) runs the full length-limited canonical code builder twice — over static_litlen_freqs() and static_offset_freqs(), which are constants — at parse/mod.rs:424 and :704. The result is byte-identical every time, in every process, forever. Four allocations and a package-merge pass per parser invocation; at T>1 that is per chunk. It is a const table wearing a constructor.

  6. Level 0 does not reach a parser, and the strategy that says it does is dead codedead

    deflate_into short-circuits level == 0 to emit_stored_block at deflate/mod.rs:219-220, and the streaming loop does the same at mod.rs:450-465. So Strategy::Fast0 → fast::run::<true> (parse/mod.rs:430), its FAST0_BLOCK_LENGTH (1 MiB), its ACCEL monomorphisation and emit_block_static_or_stored (parse/mod.rs:936) are unreachable from production — yet FAST0_BLOCK_LENGTH is what sizes SEQ_STORE_CAPACITY (parse/mod.rs:159-165) and therefore the 2.8 MB Sink that every level pays for. A dead path is setting a live allocation's size; the real bound for the routed parsers is SOFT_MAX_BLOCK_LENGTH + MIN_BLOCK_LENGTH = 305,000, which would make the store 101,760 entries — 814 KB instead of 2.8 MB.

  7. A content detector runs on the production path and changes nothingdead

    io.rs:193-198 opens the input a second time and classifies an 8 KiB sample whenever threads > 1 and level > 3. The resulting ContentType reaches only buffer_size and backend, and both are read exclusively by the verbosity >= 2 log at io.rs:209-216. It is not a CLAUDE.md #3 violation in effect (no parser is selected by it) but it is an extra open, read and allocation per file for a log line.

  8. Three doc comments describe a routing table that no longer existsdoc drift

    (a) level.rs:147-194 documents L3 as detector-gated LazyGated; the code emits Strategy::Lazy and the variant is gone. (b) parse/mod.rs:676-678 says L3 is excluded from streaming; because it is plain Lazy, level_has_resumable_parser returns true and it streams. (c) matchfinder/mod.rs's tier table assigns the fused head-table finder to "L0-1"; L0 never reaches it. A fourth, smaller one: pipelined.rs:182-187 argues that "Four is the smallest margin" for CHUNKS_PER_THREAD, which is 2 (pipelined.rs:114). CLAUDE.md's own warning — "the compression routing table in this file was once a careful code read and was wrong in every particular" — is still live in the source comments themselves.

  9. Two allocations are load-bearing for RSS and neither scales with inputalloc

    The T1 streaming path is genuinely fixed-footprint: 4,564,792 + 2,098,144 + 2,796,896 + 262,144 ≈ 9.7 MB regardless of file size. The T>1 path is not: slots (scheduler.rs:136) hold the full compressed output and staging buffers hold a chunk each, so peak RSS tracks input × (1.1 + chunk-parallelism). The MAX_T_AWARE_BLOCK_SIZE cap at pipelined.rs:118 bounds the staging half; nothing bounds the slot half.

  10. The emit path allocates nothing but rebuilds 547 table entries per block

    EmitTables::build (parse/mod.rs:1059-1085) is stack-only — 256 literal entries, 259 length entries, 32 offset entries — but it is recomputed per block from the Huffman code that was just built, and cost_from_freqs (parse/mod.rs:996) has already walked the same frequency arrays twice for the dynamic/static decision. Three passes over the same histograms per block, in a path that never appears in the hc profile and is therefore easy to leave alone.

What this drawing is not. Every anchor was read, not inferred, but nothing here was executed. The DHAT and cachegrind figures are the ones supplied with the task plus the ones banked in docs/target-encoder-and-gap-analysis.md; the arithmetic checks (4,564,792 = 2·32768 + 305,000 + 4,194,240 + 16; 5,593,792 = 2 × 349,612 × 8; 262,144 = 65,536 + 131,072 + 65,536) confirm which source line each DHAT site corresponds to, and nothing more. Any claim about what the shipped binary does still needs a route assertion and an output sha.
